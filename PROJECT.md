## Schema rules (decision)

- **All tables are `STRICT`**: every `CREATE TABLE` ends with `) STRICT;`. SQLite then rejects values of the wrong type instead of silently accepting them.
- Allowed column types: `INTEGER`, `REAL`, `TEXT`, `BLOB`, `ANY`. No `VARCHAR`, `BOOLEAN`, `DATE` and the like: yes/no values are `INTEGER` with `CHECK (x IN (0,1))`, dates are `TEXT` (ISO format) or `INTEGER`.
- `STRICT` cannot be added to an existing table: the table must be recreated. Structural changes are therefore made in `schema.sql`, then the database is rebuilt with `build_database.py`, not by hand in Letos.
- **Foreign keys**: enabling them is not stored in the file, it must be requested on every connection with `PRAGMA foreign_keys = ON;` (already in `schema.sql` and `build_database.py`). In Letos it can be checked with `PRAGMA foreign_keys;` (it must return 1).
- Status: **done**. All tables of `schema.sql` are `STRICT`. Checked that text in an `INTEGER` column (e.g. `machine.year`) is rejected.
- **Evidence** (decision): tables whose facts can be wrong have a column `evidence`: `MANUAL` (stated by a source, not tested), `TESTED` (checked on the machine or an emulator), `INFERRED` (deduced, e.g. proposed by Claude: neither stated nor tested), NULL (not assessed yet). Tables: `parameter`, `parameter_limit`, `allowed_value`, `syntax_form` (returned range and description), `character_code`, `variable_layout_field`, `program_layout_field`, `memory_area`. Examples, features and errors keep their `verified` flag. An error that comes from `parameter.error_code` counts as verified only if the parameter is `TESTED`.
  ZX80 (`data/zx80.py`): parameters with facts `MANUAL` by default (`ev=` in the parameter dict overrides it: CHR$ n and RND n `TESTED`), parameters without facts NULL; forms with a returned range `MANUAL` (`F(..., ev=...)`: the relational operators, -1/0, `TESTED`); character codes `MANUAL` except 1, 212 and 118 `TESTED`; memory rows follow `MEMORY_EVIDENCE` (`MANUAL`: from the manual, not yet checked on an emulator).
- **Open questions in the database** (decision): `open_question` (layer or machine, position, Markdown text, `resolved`, notes) holds the things to do that are not tied to one row. ZX80: `OPEN_QUESTIONS` in `data/zx80.py` (the `original_syntax` check against the printed manual).

## Web interface (decision)

- The site is **for reference only**; the data is updated only from Letos, by a **single editor**.
- Approach: **static site generated by Python** (Jinja2 templates).
- Each entry page already contains the equivalents in the other dialects, including the actions with no equivalent; search uses a JavaScript index.
- `render_syntax.py` is reused as a module by the generator.
- Alternative for a free-form translator: sql.js (SQLite in WebAssembly) in the browser.

- Uses Jinja2 alone, without Flask: enough for a reference-only site.

Below, always visible, the list of entries with a category menu (All, Statements, Direct commands, Operators…) and a search box.
- Operator precedence from the column `syntax_form.precedence`; the entry page shows the precedence of each form. Operator descriptions do not repeat it.
- Keywords: each keyword has a page (`keywords/<text>-<id>.html`, symbols with names: `quote-1`, `semicolon-4`) with tokens, abbreviations and all the entries that use it in their syntax (from the tree nodes; for entries without a tree, from the name). It is reached from the keywords panel, the entry page and the search.
- Operators: in the entry list they are divided by class (`operator_class`), and the Category menu has an item for each class. The entry page shows class and precedence of each form.
- Character codes: 16×16 grid for each character set of the dialect's machines (`v_character`), drawn in the browser from the glyph bitmaps (inverted when the screen code says so), in their own proportions whatever the size of the set (one scale for both axes: 8×8 and 5×7 at 3 screen pixels per glyph pixel, 8×16 at 2); unused codes are dimmed, tokens show the keyword, control codes their name. The machine page shows the attributes, its one-off tables and the state of the hardware tables. The tooltip shows the Unicode code point (`U+2588`), not the character, which may be missing from the visitor's fonts.
- **Markdown in the texts** (decision): long free-text fields (`notes`, `description`, `difference_notes`, and the descriptions and notes of forms, parameters, examples, features and table states) are written in Markdown: real line breaks, numbered lists (`1.`), bulleted lists (`-`), tables (`| a | b |` with the `|---|---|` row), `inline code` for BASIC code and formulas (an unquoted `*` can turn into italics), **bold** only where needed; a blank line separates paragraphs; no raw HTML (it is shown as text). Short fields (`name`, `title`, `code`, `message`, keyword `text`, values) stay plain text. The site renders them with the filters `md` (paragraphs, lists, tables) and `mdi` (table cells and sentences: no `<p>` around a single paragraph); without the markdown library the texts are shown as plain text with line breaks.
- **Diagnostics page** (decision): one per dialect, `dialects/<CODE>-diagnostics.html`, linked from the bar of the dialect page ("Diagnostics", with the number of open items). A summary with the count of each section, then the sections, each listing its rows with links to the entry or to the dialect's panel; empty sections say "Nothing left":
  1. *Open questions*: `open_question` with `resolved` = 0, for the dialect's layers and machines;
  2. *Examples*: examples with `verified` = 0; entries of the dialect without examples;
  3. *Errors*: rows of `v_entry_error` with `verified` = 0, grouped by entry (rule, detail, cause); errors of the dialect (`v_dialect_error`) that no entry uses;
  4. *Syntax*: forms whose manual syntax differs from the rebuilt one (same comparison as the "differs from the rebuilt syntax" tag); forms without `original_syntax`;
  5. *Evidence*: for `parameter`, `parameter_limit`, `allowed_value`, `syntax_form`, `character_code`, `variable_layout_field`, `program_layout_field`, `memory_area`, the counts by MANUAL / INFERRED / NULL / TESTED and the rows not TESTED (INFERRED first and highlighted more than MANUAL; character codes as ranges of codes);
  6. *Features*: `v_dialect_feature_all` answers missing (`feature_id` NULL) or not verified;
  7. *Tables*: `table_status` TO_DO or PARTIAL for the dialect's layers and machines, and table kinds without any state;
  8. *Gaps*: parameters without description, forms without actions (`form_action`), keywords without a token, variable types with `max_name_length` or `significant_chars` NULL, memory areas with `prologue` or `epilogue` NULL.
  Built by `diagnostics_context()` in `build_site.py` with the template `templates/diagnostics.html`.
- **Evidence marks** (decision): the entry and dialect pages show the evidence next to the facts, with the macro `ev_mark` (`templates/_evidence.html`): `I` full red = INFERRED, `M` outlined = MANUAL, a small ✓ = TESTED, nothing = NULL; the tooltip explains it. Entry page: next to the parameter name (`parameter.evidence`), each limit and allowed value in "Allowed values", and the returned range (`syntax_form.evidence`). Dialect page: an "Ev." column in the memory tables (variables, program), the mark after the before/after of each memory area, and in the character codes grid a corner on the cells not TESTED (faint for MANUAL, stronger for INFERRED), with the evidence in the tooltip and in the legend.
- Entry pages: arrows at the top and bottom to go to the previous and next entry of the dialect, in the order of the dialect page (by category; operators by class, each entry once), with the position (`12 / 42`); one row per dialect when the entry belongs to several. The ← and → keys follow the first row.
- Entry addresses: `entries/<name>-<id>.html`; operators use names instead of symbols (`**` → `star-star-31.html`, `<` → `lt-38.html`).

- `operator_class` (vocabulary in `data/base.sql`) and `syntax_form.operator_class_id`: Arithmetic, Bitwise, Conditional, Logical, Memory, Relational, String, Grouping. The class belongs to the form (+ is arithmetic and string; AND is bitwise, logical or conditional depending on the dialect). **Conditional** (ZX81, ZX Spectrum), with TRUE = -1 and FALSE = 0: TRUE AND e = e, FALSE AND e = FALSE, TRUE OR e = TRUE, FALSE OR e = e, NOT TRUE = FALSE, NOT FALSE = TRUE, in general NOT e = -e-1. In `data/zx80.py` it is written `F(..., op="ARITHMETIC")`.
- ZX80: entry `( )` (grouping operator). AND, OR and NOT are **bitwise** (85 OR 170 = 255, 85 AND 170 = 0): they behave as conditional operators only because comparisons give -1/0 and the only numeric type is the signed 16-bit integer (explained in the entry notes, with examples); their notes start with the one-bit truth table in Markdown.
- **Features** (decision): a fixed catalogue of questions that **every dialect answers**, kept in `data/base.sql`: `feature_kind` (code, question, typical answers, description, position) grouped in `feature_section` (subsections, so related features stay together). The view `v_dialect_feature_all` returns every dialect × every kind, with `feature_id` NULL when the answer is missing; the site shows missing answers as "not entered".
  Catalogue: *Program lines and statements* (range of line numbers, multiple statements per line, statement separator, LET mandatory/optional); *Truth values* (TRUE_VALUE, FALSE_VALUE, TRUTH_TEST); *Numbers* (conversion of non-integer values to integers, e.g. truncation towards zero); *FOR loops* (body always executed at least once, loop variable changeable inside the loop); *Keyboard* (modal keyboard for keywords: Yes / No / Both); *Screen output* (width of the fixed tabulation zones, variable tab stops). - Notes on tables: every always-present table has notes for the whole table (`table_status.notes`, e.g. the ZX80 error format `n/m`, shown above the error list); each row has its own description or notes column.

  Where a keyword has no abbreviation (e.g. ZX80 functions, typed letter by letter), its abbreviation is the **empty string**; the site shows it as "none". Every keyword, symbols included, can have an abbreviation.

## Goals

1. Choose a **machine**, see its **dialects** and read their entries like a reference manual.
2. Rich entries: type, syntax, tokens, abbreviations, parameters, examples, sources.
3. A **translator** that finds equivalences between dialects, which are almost never 1:1.
4. **Rebuild the syntax** of each form from the definition of its parameters.
5. Querying from a web interface.

## 1. Layers: dialects as stacks of layers

- A **layer** (`layer`) is a core (`CORE`) or an extension (`LAYER`): `BASIC_1.0_core`, `BASIC_2.0_layer`, `Simons_BASIC_layer`…
- A **dialect** is an ordered stack of layers (`dialect_layer.position`, 1 = core). The same layer can be reused in different stacks.
- A **machine** hosts one or more dialects (`machine_dialect`: ROM, cartridge, disk…).
- Every row that follows the layers has `layer_id`, `operation` (`ADD` / `REPLACE` / `REMOVE`) and `redefines_id`. **The layer with the highest position wins; `REMOVE` hides the row.**
- A redefinition **copies the whole entry**, not just the differences. `redefines_id` points to the previous entry and `difference_notes` explains what changes (e.g. INPUT that in the core accepts only numbers and in a later layer also strings and a prompt).
- These follow the layers: `entry`, `keyword`, `data_type`, `variable_kind`, `parameter_kind`, `error`, `construct`, `feature`. The `v_dialect_*` views return the rebuilt dialect.

Example: the C64 shows *BASIC 2.0* = core 1.0 + layer 2.0 and *Simons' BASIC* = core 1.0 + layer 2.0 + Simons layer.

## 2. Lexicon and syntax are separate

- **Lexical level**: `keyword` (PRINT, GOTO, TO, STEP, THEN…), with `token` and `abbreviation`. `?` is the abbreviation of the keyword PRINT, not of the statement.
- **Syntactic level**: `entry` (the manual page: "FOR...TO...STEP", "NEXT", "MID$"), which uses the keywords through its own syntax tree.
- Entries that overlap between layers are matched by **name + category** (MID$ function and MID$ statement are different entries). Keywords are matched by their text.
- Tokens and abbreviations have an **optional** `machine_id`: empty = valid everywhere; set = valid for that machine and it overrides (conservative assumption). Tokens are byte sequences in hexadecimal, so they also handle 2-byte tokens (e.g. `FE02`).
- Blocks are linked with `reference.kind = 'OPENS_BLOCK'` (FOR→NEXT, GOSUB→RETURN, WHILE→WEND, DO→LOOP).

Possible future use: a **detokenizer** for .PRG files (tokenizing is not a goal).

## 3. Syntax forms and actions (the translator)

- An entry has one or more **syntax forms** (`syntax_form`).
- **Rule**: what changes the *action* becomes a separate form (plain LINE / `,B` / `,BF`). What only changes the *way of writing* is a choice inside the tree (relative or polar coordinates).
- **Actions** (`action`, grouped in `action_group`) are linked to forms by `form_action`, with `coverage` (`FULL` / `PARTIAL`) and notes (e.g. "relative coordinates").
- `v_equivalence` returns the forms of different dialects that share an action. `v_uncovered_action` returns the actions with **no equivalent** in the target dialect.

Checked on the test data:

| From | To | Result |
|---|---|---|
| DRAW (Spectrum) | GW-BASIC | Line → LINE (PLOT_LINE); Arc → CIRCLE (PLOT_ARC) |
| CIRCLE (GW-BASIC) | Spectrum | Circle → CIRCLE; Arc → DRAW; Ellipse → **no equivalent** (PLOT_ELLIPSE) |

## 4. Types and parameters

**Data type, variable type and parameter type are three different things** (decision):

- **Data type** (`data_type`, follows the layers): the values. ZX80: integer [-32768, 32767]; string of any length, empty included. Suffix, type class, minimum, maximum, precision, bytes. **The limit that depends on the type comes from here** and is not repeated in the statements.
- **Variable type** (`variable_kind`, follows the layers): the variables, which also differ in their memory representation. Data type of the value or elements, number of dimensions (0 = scalar), naming rule in words and as an optional regular expression, name length without the type suffix: **maximum length** (`max_name_length`: 0 = no limit) and **significant characters** (`significant_chars`: 0 = all) — some dialects accept names of any length but only the first characters count, others count every character but limit the length (NULL = not entered), examples; the memory layout is in `variable_layout_field`. ZX80: numeric variable (letter followed by letters or digits, no length limit, all characters significant: `A`, `PIPPO24`), string variable (one letter + `$`, maximum length 1: `A$`, `Z$`), numeric array (one letter, maximum length 1, one dimension: `B(5)`, `F(12)`), loop control variable (one letter, maximum length 1); in all of them every character is significant. Memory layout entered for all of them.
- **Parameter type** (`parameter_kind`, follows the layers): what can be written for a parameter. A nature (LITERAL, EXPRESSION, CONDITION, VARIABLE, ARRAY_NAME, ARRAY_ELEMENT, FREE_TEXT, STATEMENT) plus a type class (for literals, expressions and conditions) or a variable type (for names; empty = any variable). ZX80, 12 types: numeric literal, string literal (in quotes), numeric expression, string expression, numeric variable name, string variable name, numeric array name (`B`), numeric array element (`B(3)`), loop control variable name, free text (after REM), statement (after THEN), condition (after IF). Some dialects write the array name with empty parentheses (`B()`): to be handled when such a dialect is entered.
- `type_class`: families shared by all dialects (NUMERIC, INTEGER, REAL, STRING, BOOLEAN, ANY). It does not follow the layers; it is used by data types and parameter types.
- **Truth values** (decision): a few dialects have a native **boolean** type (type class BOOLEAN, values TRUE/FALSE); most give numbers (of any numeric type) a boolean reading. Three dialect features with fixed codes (they follow the layers): `TRUE_VALUE` = value produced by a true comparison (-1 in many dialects, 1 in others), `FALSE_VALUE` = 0, `TRUTH_TEST` = how a value used as a condition is read (`NONZERO`: true if not 0). Some rare dialects also read the empty string `""` as false and a non-empty string as true. ZX80: -1, 0, `NONZERO`; AND, OR and NOT work bit by bit, so NOT 1 = -2 is true.
- **Condition** (decision): parameter type with nature CONDITION, for the places where a value is reduced to a truth value (after IF). It is usually a relational expression whose terms can also be strings (`A$="Y"`). ZX80: numeric condition, read with the truth test.
- BBC BASIC (to be checked when it is entered): TRUE and FALSE are keywords that behave like functions without arguments (they give -1 and 0) and cannot be assigned: `TRUE=5` is a relational expression, not an assignment.
- The parameter type is set on each **PARAMETER node** of the syntax tree (`syntax_node.parameter_kind_id`), not on the parameter: a parameter that accepts several types is a choice of nodes pointing to the same parameter (LET: numeric variable or array element = numeric expression, or string variable = string expression). When rendering, choices that look the same are written once, so the syntax stays `LET variable = expression`. The node has no parameter type only when the parameter is a construct.
- A parameter can be a **construct** (`construct_type_id`). **A form returns a concrete type** (`syntax_form.return_type_id`, with minimum and maximum: SIN → real, from −1 to 1).
- `parameter`: `conversion` (NONE / TRUNCATE / ROUND), `table_kind_id` (e.g. COLORS), `error_code` (e.g. ILLEGAL_QUANTITY: only the error given for a value that is **not allowed** for that parameter; errors due to the context, like ZX80 INPUT used as a command, go in `entry_error`: see *Errors of each entry*), `missing_line` for line numbers. The site shows the error as the dialect defines it (number and message, e.g. ZX80 NEXT: error 1 `1/n`).
- **Line numbers** (decision): the rules depend on the dialect and even on the statement (compare GOTO and LIST in Commodore BASIC). `parameter.missing_line` says what happens when the line does not exist: `NEXT_LINE` (the next existing line is used: ZX80 GO TO, GO SUB, RUN, LIST) or `ERROR`. The range of the program line numbers is a dialect feature (ZX80: 1-9999, entering line 0 gives an error); stricter ranges of a parameter go in `parameter_limit`.
- `parameter_limit`: limits imposed by the statement, with inclusive or exclusive bounds (RND: from 0 inclusive to 1 exclusive), optional `machine_id` (PLOT: screen size) and notes for limits that depend on the context (SCREEN mode).
- `allowed_value`: discrete, non-contiguous values.

## 5. Syntax tree

Each form (and each construct) has a tree in `syntax_node` (`parent_id`, `position`).

| Kind | Notation | Meaning |
|---|---|---|
| SEQUENCE | | children in a row |
| CHOICE | `< a \| b >` | exactly one of the children |
| OPTIONAL | `[ ]` | optional content |
| REPEAT | `x[,x]...` | repeated `min_occ`..`max_occ` times, with `separator` |
| LIST | `[a][,b][,c]` | optional children; separator **only between present items** |
| LITERAL | text | punctuation and prefixes (`,` `;` `(` `D` `U` `+`) |
| KEYWORD | text | reference to `keyword` |
| PARAMETER | name | reference to `parameter` |
| CONSTRUCT | | inserts a construct |

- The **parameter type** (expression, variable name, literal…) belongs to the **node**, not to the parameter: in DIRECTORY the same parameter *drive* is written `D0` (numeric literal, attached) or `D(DV)` (numeric expression in parentheses).
- `attached` = no space before. `meaning` explains literals that are not plain punctuation (`+` = relative position).
- In a LIST, a child can have its own separator: its first node has `only_if_preceded = 1` (e.g. `<ON | ,>` before the unit in DIRECTORY).
- Placeholder commas (BOX `,10,10,60,60,45,1`) are obtained by putting the literal **outside** the optional node.
- **Constructs**: reusable sub-grammars (e.g. COORDINATE in BASIC 3.5/7.0), which follow the layers. A parameter whose type is a construct is a single parameter: one component cannot be omitted while keeping the other.
- `original_syntax` keeps the manual's syntax together with the source. Manuals are imprecise (DIRECTORY): comparing it with the rebuilt one is useful information.

Examples rebuilt by `render_syntax.py` (from the test data and the ZX80):

```
BOX [color source], X1,Y1[,X2,Y2][,[angle][,paint]]
DIRECTORY [D<drive | (drive)>][<ON | ,> U<device number | (device number)>][,<wildcard | (wildcard)>]
INPUT[;] ["prompt"<; | ,>] variable[,variable]...
COORDINATE: <[+ | -]x,[+ | -]y | distance;angle>
PRINT [item][<; | ,>[item]]...      (ZX80)
```

## 6. Tables that always exist (decision)

These tables exist for every dialect or machine, even when they are not defined for a particular combination. `table_kind` is their catalogue (code, name, **scope**, display order); `table_status` records, for each layer (DIALECT scope) or machine (MACHINE scope), whether the table is `NOT_APPLICABLE` (it does not exist there), `TO_DO`, `PARTIAL` or `COMPLETE`, with notes valid for the whole table.

| Table | Scope | Where |
|---|---|---|
| Glyphs | machine | `charset`, `glyph` |
| Character codes (ASCII, PETSCII, ATASCII…) | dialect | `character_code` |
| Screen codes / video memory | machine | `screen_code` |
| Keyboard codes | dialect | `key_code` |
| Error messages | dialect | `error` |
| Operator precedence | dialect | `syntax_form.precedence` and `associativity`, view `v_operator_precedence` |
| Variables in memory | dialect | `variable_layout_field` |
| Program in memory | dialect | `program_layout_field` |
| Color codes and attributes | machine | `color`, `attribute` |
| Musical notes | dialect | `musical_note` |

- **Character code → screen code → glyph** are three levels. `character_code` (follows the layers) says what each code means for the BASIC: `PRINTABLE` (prints a screen code), `CONTROL` (performs an action), `TOKEN` (prints the keyword with that token), `UNUSED` (no meaning; the screen code it prints, if any). Character codes belong to the dialect because extensions give meanings to control codes (Simons' BASIC, VIC-20 Super Expander); `mode` distinguishes codes that change with the video mode (C128: 40/80 columns). `screen_code` (machine) maps each value in video memory to a glyph number and says whether the hardware inverts it. `glyph` holds one bitmap per glyph number. `v_character` follows the whole chain for each machine and dialect.
- **Keyboard codes** (dialect): the code the BASIC gives for a key, also for keys without a character code (PgUp, NumLock read with INKEY in GW-BASIC or BBC BASIC), and the keyword a key enters (ZX80 K mode). Optional `machine_id`.
- **Musical notes** (dialect): the value written in the sound statement for each note (e.g. ZX Spectrum BEEP: semitones). When the statement wants a frequency (C64), the formula goes in the notes of `table_status`.
- **Operator precedence**: now also with associativity (`LEFT` / `RIGHT`) at equal precedence; the old text feature was removed.
- **Memory**: `variable_layout_field` (fields of each variable type) and `program_layout_field` (fields of a program line), each with position, offset, size, byte order and description. A variable type can be stored in more than one way: `layout` and `layout_name` (ZX80 numeric variable: name of one character / name of more than one character). `memory_area` (follows the layers) says what comes before (`prologue`) and after (`epilogue`) the program and the variables area: `''` = nothing, NULL = not entered.
- **Attributes**: `attribute` (machine), next to `color` (e.g. INK, PAPER, BRIGHT, FLASH on the ZX Spectrum).
- **One-off tables** for special cases (e.g. the C128 escape sequences): a generic grid on a layer or a machine (`custom_table`, `custom_column`, `custom_row`, `custom_cell`).
- A parameter can point to a table **kind** (`table_kind_id`, e.g. COLORS); the actual table depends on the machine being viewed.
- **Tables used by an entry** (decision): found automatically, for entries (not keywords), by the view `v_entry_table_kind` (entry, table kind, rule, detail); the entry page lists them under "Tables", with links to the dialect's panels. Criteria:
  1. transcoding (ASC, CODE, CHR$…) → character codes (actions STR_CHR, STR_CODE);
  2. character redefinition (TI-99 CALL CHAR…) → the table of the encoding the statement uses, usually the screen codes (parameter `table_kind_id`);
  3. keyboard reading → the table of the encoding of the returned value (GET, INKEY$ → character codes; GW-BASIC INKEY$ also keyboard codes, entered by hand in `form_table_kind`);
  4. graphics statements with a color → color codes / attributes (parameter `table_kind_id`);
  5. sound statements with an encoding of the notes → musical notes (parameter `table_kind_id`);
  6. operators → operator precedence (forms with `precedence`);
  7. variable assignment (LET, =, READ, INPUT), also the FOR loop variable, and creation and deletion of variables (DIM, CLEAR) → variables in memory (actions VAR_LET, IO_INPUT, FLOW_FOR, FLOW_NEXT, VAR_DIM, VAR_CLEAR);
  8. jumps to program lines (also RUN n, LIST n, CONTINUE, RETURN) and saving/loading programs, not generic memory blocks → program in memory (actions FLOW_GOTO, FLOW_GOSUB, PROG_RUN, PROG_LIST, FLOW_CONTINUE, FLOW_RETURN, TAPE_SAVE, TAPE_LOAD).
  The action rules are in `action_table_kind` (`data/base.sql`); `form_table_kind` adds the links the rules cannot see.
- **Notes from the features** (decision): the dialect features are shown automatically in the entries they concern, by the view `v_entry_feature_note` (dialect, entry, form, parameter, target, feature, value) built from the rules in `feature_note_rule` (`data/base.sql`). Each rule picks entries by a line-number parameter (`missing_line` set), a parameter nature (e.g. CONDITION), an action or an operator class, and puts the feature in the parameter's allowed values (ALLOWED), next to the form's returned value (RETURN) or in the entry notes (NOTE). Rules:
  - range of line numbers → allowed values of every line-number parameter (ZX80: GO TO, GO SUB, LIST, RUN);
  - LET mandatory/optional → notes of the assignment (action VAR_LET: LET, and `=` as assignment in other dialects);
  - TRUE_VALUE and FALSE_VALUE → returned value of relational, logical and conditional operators; TRUTH_TEST → allowed values of conditions (IF) and notes of logical and conditional operators. Bitwise operators (ZX80 AND, OR, NOT) get all three in their notes, so the reader sees why they work in conditions (comparisons give -1/0, read with the truth test);
  - FOR body executed at least once, loop variable changeable → notes of FOR...TO, NEXT (and FOR...TO...STEP: same actions);
  - fixed tab zone width, variable tab stops → notes of PRINT.
  The texts that repeated these facts by hand were removed (ZX80 LET description, FOR...TO notes). Values not verified show the "to verify" tag; with several dialects, each value is followed by the dialect name.
- **Errors of each entry** (decision): every entry lists the errors it can give, in the view `v_entry_error` (dialect, entry, form, parameter, error, rule, detail, cause, verified). Errors are named by their code and found in each dialect through `v_dialect_error`. Sources:
  1. `entry_error` — written for the entry, with optional form and parameter, a cause (Markdown) and `verified`. With `operation = 'REMOVE'` it takes away an error the other sources would give (ZX80 LIST n: an error while computing n is not reported);
  2. `parameter.error_code` — the error for a value not allowed (ZX80 NEXT: error 1), repeated automatically;
  3. `error_rule` (DIALECT scope: a rule applies in the dialects that contain its layer; no REPLACE/REMOVE) — errors common to many entries, chosen by parameter kind (e.g. NUM_EXPR), action or operator class (e.g. ARITHMETIC). ZX80 rules: numeric expressions, string expressions and conditions → 2 (undefined variable), 3 (subscript), 6 (overflow); array elements → 2 (not dimensioned), 3; arithmetic operators → 6.
  The entry page has an "Errors" section: one line per error and cause, with the parameters and forms it comes from (forms named only if the error does not concern all of them), "automatic" for errors from rules or parameters, "to verify" if not verified; with no cause the error description is shown. ZX80 data (`ERROR_RULES`, `ENTRY_ERRORS` in `data/zx80.py`) were proposed by Claude: all to verify except those the data already stated (PRINT 5, INPUT 8, RETURN 7, STOP 9, NEXT 1, LIST n without errors) and those checked on an emulator (`/` by zero → 6, DIM with a negative size → 3).

### Character sets and glyphs

- `charset`: one or more sets per machine (e.g. the two C64 sets), with glyph width and height in pixels.
- **National variants** (e.g. C128 it, de, fr, es): a set with `base_charset_id` and `language` holds **only the glyphs that differ**; the others are inherited from the base set, also over several levels. `v_effective_glyph` returns all resolved glyphs for each set, with `source_charset_id`. A variant is defined for each base set (e.g. upper case/graphics and lower/upper case on the C128, each with its own variants).
- `glyph`: bitmap in hexadecimal, one pixel row per byte, bit 7 on the left (8×8 = 16 digits). A trigger checks that the length matches the dimensions of the set. Extra columns: `inverse_of` (glyph of the same shape in normal video), `unicode` (equivalent of the shape, if any: blocks `▌▄▘…`, shades `▒ 🮏 🮎`), `unicode_name` (its official Unicode name, e.g. `LOWER HALF MEDIUM SHADE`, shown in the tooltip; in `data/zx80.py` the names are written out, so they do not depend on the Unicode version of Python), `name`.

### ZX80

- 128 glyphs and 128 screen codes (0-63 and 128-191, the second half in inverse video), each screen code showing the glyph with the same number; bitmaps taken from `data/sources/zx80_charset.png` and written in `data/zx80.py`. The image confirms the order `=` `>` `<` of codes 22-24.
- 256 character codes: 128 printable, 2 control, 39 tokens (213-254, except 241, 242, 245), 87 unused printed as `?` (64-127 except 118, 192-211, 241, 242, 245, 255). Printable codes show the screen code with the same number (0-63 and 128-191), except two: **the order of the glyphs in the ROM is not the internal character code** of the ZX80 (a proprietary encoding, not ASCII). Glyph 1 is the quote, but code 1 is not printable (`PRINT CHR$(1)` prints nothing): it is the string terminator (control) and the byte with which typed quotes are stored in the program, so the keyword `"` has token $01 (checked on an emulator: `10 PRINT "ABC"` is stored as `0 10 244 1 38 39 40 1 118`; the manual's token table lists $D4). The printable quote is code 212 (screen code 1): it cannot be typed from the keyboard but can be put in string variables. Code 118 ($76) is NEWLINE (control, end of a program line).
- Table states: glyphs, screen codes, character codes, errors, operator precedence, program in memory, variables in memory complete; keyboard codes (the ZX80 BASIC has none), colors (black and white display) and musical notes (no sound) do not exist.
- Random numbers (notes of RND, the first text written in Markdown: a numbered list, one step per line, formulas as inline code): seed n (read as an unsigned 16-bit number, so -5 is 65531; 0 counts as 65536), `m = (n*77) MOD 65537` (65536 counts as 0), `RND(x) = u*m/65536 + 1` where `u = x AND 65535` (x as an unsigned 16-bit number), result read as a signed 16-bit integer, then n = m. So RND(n) with n<0 gives 1 to 32767 or -32768 to n (the manual says -32768 to n-1). Checked against the first 23 values of `RANDOMISE 5` with `RND(100)` and with `RND(-10)` on an emulator and of `RANDOMISE -5` with `RND(100)` (all entered as verified examples).
- Edge cases checked on an emulator (each also entered as a verified example): `PRINT 1/0` → `6/-2`; `DIM A(-10)` → `3/-2` (a direct command reports line -2, now also in the notes of the error table); `ABS(-32768)` cannot be typed (the syntax check rejects 32768), but `ABS(-32767-1)` wrongly gives -32768 with no error — a ROM bug, kept in the notes of ABS while its returned range stays 0..32767; CHR$ takes its argument modulo 256 (`CHR$(256+38)` = `CHR$(38)` = A; the old 0-255 limit was removed); `CODE("")` gives 1 (the string terminator); `TL$("")` gives the empty string.
- Memory: program line = line number (2 bytes, big endian), tokenized text, NEWLINE ($76); nothing before the program, `$00, $00` after it. Variables area: nothing before, `$80` after. Integer values little endian (also array elements and the loop limit); the line number of a loop control variable (FOR line + 1) is big endian.

LIST, CLEAR, SAVE and LOAD each have two forms, *Current area* and *All areas* (`LIST A`...): the `A` is a literal letter with no token of its own, so they are one entry each, not separate entries.
- Keyboard: S + letter gives the statements, F + letter the functions (abbreviations `S + A` = GOSUB, `F + A` = SIN, ...); S + digit selects the program area. Errors are shown as `ERRn Pa-l` (area and line); there is no error 8.
- **Codes** (from bas2fx70.c and the image of the glyphs): the internal code of a character is the position of its glyph in the 16x8 image, not ASCII: space $00, + - * / ↑ $01-$05, ! " # $ $06-$09, > ≥ = ≤ < ≠ $0A-$0F, digits $10-$19 (zero slashed), . $1A, π $1B, ) ( $1C $1D, exponent signs ᴇ- $1E and ᴇ $1F, A-Z $20-$39, a-z $40-$59, ? , ; : $5C-$5F, symbols $60-$79 (○ Σ ° △ @ × ÷ ♠ ← ♥ ♦ ♣ μ Ω ↓ → % ¥ □ [ & _ ' · ] ■). Codes $80-$C6 are **tokens** (one byte: functions $80-$97, statements $A0-$AA, $B0-$B3, commands $C0-$C6); the tokens of LEN(, VAL(, MID( and RND( include the parenthesis, so those keywords are written with it. $FE = colon between statements, $FF = end of line. 14 codes have a blank glyph (UNUSED, INFERRED); bas2fx70 maps @ to $65 (× in the image) and \ to $7A (blank): open question. Operators and π have their character code in the token table, with a note.
- **Memory** (source: P. Piatek, "Casio FX-700P - data formats"; MANUAL unless said otherwise): the RAM has 4-bit words, a byte takes two addresses (low nibble first), so the field offsets are in bytes only for whole bytes and the descriptions give the nibbles. Program line: line number in BCD, lower two digits first (1234 → bytes `$34 $12`, nibbles 4 3 2 1), the text (tokens, characters; numbers as digits, spaces not stored), `$FF`. Programs P0-P9 at $0220-$0E5F (3136 nibbles = 1568 steps); the `$E0` ending each program area is INFERRED from the SAVE A files. Memories at the end of the RAM, 16 nibbles each, A at $0FF0 going down to Z at $0E60, then the expanded ones (taken from the program area). - Tables: glyphs, errors, variables in memory and program in memory complete; operator precedence partial (functions before the power, as in the manual's example `2+3*SIN(17+13)↑2` = 2.75; the change of sign is placed before the power as in PokecomGO2, `-2↑2` = 4, not tested on the real machine); character codes and screen codes (assumed: code n shows glyph n) partial; keyboard codes to do; colors and musical notes not applicable.

- **What each edition adds**: 1st: LET (mandatory), PRINT (commas, labels), END, FOR/NEXT (loop variable a single letter), GO TO, IF...THEN (jump only), DEF FNx(one argument), READ, DATA (200 numbers), GOSUB/RETURN (no nesting), DIM, REM; SIN COS TAN ATN EXP LOG SQR (of the absolute value) ABS RND(x) INT (truncation); ↑ uses the absolute value of the base; unary minus before the power (`-X↑2` = `(-X)↑2`); lists and tables from 1 (source: Wikipedia); line numbers 1-99999; commands HELLO, RUN, LIST, SAVE, STOP. 2nd: STOP, `;` in PRINT, subscripts from 0 to 10, NEW, OLD, SCRATCH, RENAME, CATALOG, UNSAVE, LIST-n. 3rd: INPUT, RESTORE, MAT READ / MAT PRINT / MAT (9 forms), SGN (Wikipedia only), INT = floor, unary minus after the power, negative base with integer exponent, nested GOSUB, run-time messages (DIVISION BY ZERO, OUT OF DATA, RETURN BEFORE GOSUB, ...), LENGTH, SYSTEM. 4th: strings (A$, C7$, V$(n)), LET with several variables, PRINT TAB, ON...GO TO / THEN, RANDOMIZE, CHANGE, DEF without argument and multi-line DEF with FNEND, `'` remarks, RND without argument, COT, NUM, DET, MAT INPUT, MAT copy, RESTORE* and RESTORE$, BYE, REPLACE; numbers of the GE-635 (largest about 1.70141E38, inferred from EXP TOO LARGE); errors renamed (ILLEGAL FORMAT, UNDEFINED LINE NUMBER, NEXT WITHOUT FOR, ...).
- **October 1964 manual** read in full (PDF page = printed page + 6): appendix A confirms the 22 messages, appendix B the limits (in the notes of the 2nd edition error table). The 2nd edition also redefines FOR...TO...STEP and NEXT (any unsubscripted variable, `FOR X1`) and DATA (300 numbers).
- **Character set** (decision): the Teletype ASR-33, 64 characters, codes 32-95 of ASCII-1963, upper case only (94 ↑, 95 ←). Each machine has a charset `ASR33_<machine>` (language `us`) of 64 glyphs and a national variant `ASR33_UK_<machine>` (language `uk`, `base_charset_id` = the US set) holding only the pound sign at code 36 (the UK print head printed £ where the US head printed $; glyph 0x60 of the font). They are a **reconstruction** rasterized from the font in `data/sources/teletype.ttf`. Two rasterizations are kept in `data/dartmouth.py`, `ASR33_GLYPHS_16` and `ASR33_GLYPHS_24` (one scale for all glyphs, the ink band mapped to rows 1-14 or 1-21, centred, box filter, ink > 45 %); `GLYPH_SIZE` = 24 (the editor's choice) picks the one entered; screen codes 32-95 → the glyph with the same number, only as the link code → glyph (no screen). Character codes 0-127 in the core, INFERRED (32-95 printable, EOT 4, BELL 7, LF 10, CR 13, RUB-OUT 127 control, 96-126 lower case unused); the 4th edition REPLACEs the listed codes as MANUAL from the CHANGE table, p. 68 of its PDF. Card BASIC inherits them, with its character table TO_DO (card and printer codes not entered).
- **Examples from DTSS-Win**: the 18 BAS* programs and the BASIC programs of its LIB (not AVELOG, already entered from the May manual, nor FTBALL, 5.7 KB) are examples with source [8] and the file name as page, `^` written as ↑: with `;`, subscript 0 or STOP in the 2nd edition entries, with INPUT in the 3rd, the others in the core. The outputs run by the editor (all BAS*, BASLIS and the LIB programs; GUESS with one short game) are in `DTSSWIN_OUTPUT` as verified expected results, error messages included; MORT keeps only its first and last lines; `DTSSWIN_NOTE` adds remarks on single runs (NORMAL loses its last step to rounding, QUAD shows SQR of a negative number going on). AVELOG, run too, marks the manual example of LOG as verified.
- **Tests on DTSS-Win** (compiler of February 1965, run by the editor; verified examples): `-X↑2` = 9, INT(-7.8) = -7, `FOR Z = 2 TO -2` leaves Z = 1, A(0) and `FOR X1` accepted, a syntax error stops the run (`ILLEGAL FORMULA IN 20`). It already behaves like the 3rd edition: `(-2)↑3` = -8, nested GOSUB work, run-time messages that do not stop (`SQUARE ROOT OF NEGATIVE NUMBER`, `LOG OF NEGATIVE NUMBER`) and `OUT OF DATA IN n` that stops; `1/0` prints 1 with no message. RND gives the same sequence on every RUN (GUESS: 75, then 20); an unreadable INPUT value gets `INPUT DATA NOT IN CORRECT FORMAT. RETYPE IT.`; statements in lower case are rejected at RUN (`ILLEGAL INSTRUCTION`); round brackets in a label are printed as square ones (`PRINT "()"` gives `[]`, cause unknown, open question). Notes on the 1st edition entries, not corrections of the 1964 manuals. Variables and program in memory are TO_DO; keyboard codes and musical notes NOT_APPLICABLE. No tokens (the program is kept as text) and no abbreviations.

## Typical queries

Manual of a dialect:

```sql
SELECT e.name, c.name AS category, e.description
FROM v_dialect_entry de
JOIN dialect d  ON d.id = de.dialect_id
JOIN entry e    ON e.id = de.entry_id
JOIN category c ON c.id = e.category_id
WHERE d.code = 'SINCLAIR_ZX80_4K'
ORDER BY e.name;
```

Translation of an entry:

```sql
SELECT fa.title AS form, eb.name AS equivalent, fb.title AS equivalent_form,
       a.code AS action, q.from_coverage, q.to_coverage
FROM v_equivalence q
JOIN dialect d1 ON d1.id = q.from_dialect_id
JOIN dialect d2 ON d2.id = q.to_dialect_id
JOIN entry ea ON ea.id = q.from_entry_id
JOIN entry eb ON eb.id = q.to_entry_id
JOIN syntax_form fa ON fa.id = q.from_form_id
JOIN syntax_form fb ON fb.id = q.to_form_id
JOIN action a ON a.id = q.action_id
WHERE d1.code = 'SINCLAIR_BASIC_48K' AND d2.code = 'GW_BASIC' AND ea.name = 'DRAW';
```

Effective tokens of a machine: `SELECT text, hex_value FROM v_machine_token WHERE machine_id = …`.
